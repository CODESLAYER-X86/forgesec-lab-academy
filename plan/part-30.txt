# **Part 30 — Homepage, Navigation & Public Interface**

**Objective:** Design the public-facing experience of FORGESEC ACADEMY so visitors can quickly understand the platform, discover learning materials and begin learning without being forced to register.

The homepage should not look like a generic corporate website or an advertisement for a cybersecurity company. It should feel like a practical technical learning platform.

## **1. Public interface architecture**

The public interface consists of:

1. Homepage.
2. Global navigation.
3. Learning catalog.
4. Learning path pages.
5. Lesson pages.
6. Write-ups.
7. Resources and glossary.
8. Search.
9. Login and student entry points.
10. Footer and legal links.

Suggested route structure:

```
/
├── /learn
│   ├── /tutorials
│   ├── /paths
│   ├── /paths/[slug]
│   └── /lessons/[slug]
├── /writeups
│   └── /[slug]
├── /resources
│   ├── /[slug]
│   └── /glossary
├── /search
├── /about
├── /login
├── /dashboard
└── /admin
```

Use the route conventions already established in previous parts. Avoid creating duplicate routes for the same content.

### **Section 1: Hero**

The first screen must communicate:

- What FORGESEC ACADEMY is.
- What visitors can learn.
- Why they should explore it.
- Where they should start.

Recommended headline:

**Build skills. Understand systems. Learn security.**

Avoid exaggerated claims such as "Become an expert hacker in 30 days."

### **Section 2: Learning paths**

Show the main learning paths as cards.

Each card should display:

- Path title.
- Short description.
- Difficulty.
- Number of published lessons.
- Estimated learning time, if reasonably established.
- Progress indicator for authenticated students.

Visitors should be able to open a path without logging in.

### **Section 3: Latest content**

Display a small selection of recently published content:

- Tutorials.
- Technical write-ups.
- Guides.
- Reference materials.

Content should be automatically retrieved from the Git-managed content registry.

Do not manually maintain homepage content lists in the database.

### **Section 4: Why FORGESEC ACADEMY?**

Explain the educational approach:

- Practical and structured learning.
- Free access to public learning materials.
- Self-paced progression.
- Technical explanations with commands and examples.
- Responsible security practices.

Keep this section short. The quality of the actual lessons should prove the platform's value.

### **Section 5: Student invitation**

Explain the benefits of creating an account:

- Track completed lessons.
- Save bookmarks.
- Continue learning from the dashboard.
- Take quizzes.
- Track assignment progress.

Do not block public content behind authentication.

### **Section 6: Footer**

Include:

- About.
- Contact.
- Privacy policy.
- Terms of use.
- Responsible disclosure / security contact, if established.
- Copyright and platform identity.

## **3. Global navigation**

Use a consistent navigation bar across public pages.

**Desktop:**

```
[FORGESEC ACADEMY]

Learn ▼   Write-ups   Resources   About   [Search]   [Login]
```

For authenticated users:

```
[FORGESEC ACADEMY]

Learn ▼   Write-ups   Resources   About   [Search]
                                      [Dashboard] [Profile]
```

### **Navigation rules**

- Logo returns to homepage.
- Learn opens the learning catalog.
- Write-ups opens published write-ups.
- Resources opens guides and references.
- Search opens the search interface from Part 26.
- Login starts Google OAuth.
- Dashboard is visible to authenticated students.
- Admin links appear only to authorized administrators.

Do not show admin navigation to ordinary students.

## **7. Write-ups interface**

Routes:

```
/writeups
/writeups/[slug]
```

Write-ups should have their own content identity.

Recommended metadata:

- Title.
- Summary.
- Author.
- Publication date.
- Category.
- Tags.
- Difficulty.
- Target technology or vulnerability class, where appropriate.

Write-ups should support:

- Technical explanations.
- Code blocks.
- Command examples.
- Screenshots and diagrams when useful.
- References.
- Responsible disclosure context.

For security-related write-ups, distinguish authorized lab exercises from real-world testing. Do not publish private information, credentials or instructions that facilitate unauthorized compromise.

## **8. Resources and glossary**

Routes:

```
/resources
/resources/[slug]
/glossary
/glossary/[term]
```

Resources should be a structured collection of reference materials.

Examples:

- Linux command reference.
- Networking terminology.
- HTTP status codes.
- Common security terminology.
- Protocol explanations.
- Useful technical documentation links.

Glossary pages should be lightweight, searchable and linked to relevant lessons.

For example, a lesson discussing DNS should link to the DNS glossary entry.

This creates internal navigation without requiring a complex recommendation engine.

## **9. Responsive design**

The interface must work on:

- Desktop.
- Laptop.
- Tablet.
- Mobile.

Recommended behavior:

| Element           | Desktop            | Mobile                      |
| ----------------- | ------------------ | --------------------------- |
| Main navigation   | Horizontal         | Collapsible menu            |
| Learning catalog  | Multi-column       | Single column               |
| Lesson curriculum | Side panel         | Collapsible drawer          |
| Table of contents | Side panel         | Collapsible section         |
| Code blocks       | Full content width | Horizontal scrolling        |
| Search            | Dialog             | Full-screen or large dialog |

Do not simply shrink the desktop design to fit a phone.

For example, a three-column lesson layout should become a focused single-column reading experience on mobile.

## **10. Accessibility requirements**

The public interface must support:

- Keyboard navigation.
- Visible focus indicators.
- Semantic HTML.
- Proper heading hierarchy.
- Accessible form labels.
- Sufficient color contrast.
- Meaningful link text.
- Screen-reader-friendly menus.
- Reduced-motion preferences.

Use buttons for actions and links for navigation.

Do not make clickable elements out of ordinary text containers.

## **12. Performance and rendering strategy**

The public platform is primarily a content website.

Therefore:

- Use Server Components by default.
- Generate static pages for Git-managed published content wherever practical.
- Avoid unnecessary client-side JavaScript.
- Load images with optimized dimensions and formats.
- Lazy-load below-the-fold media.
- Keep navigation lightweight.
- Reuse the static search index.
- Avoid fetching student-specific data for anonymous visitors.

**Important:** Student-specific progress must never leak through shared static or cached responses.

A public lesson can be statically rendered, while progress indicators and completion controls can be loaded through an authenticated, appropriately protected mechanism.

## **13. Homepage content management**

The homepage should not require a CMS.

Use a small configuration file for curated sections:

```
content/
├── config/
│   └── homepage.yaml
├── paths/
├── lessons/
├── writeups/
└── resources/
```

Example:

```
featured_paths:
  - linux-fundamentals
  - networking-fundamentals

latest_content_limit: 4

show_student_invitation: true
```

The content registry automatically supplies the latest published content.

This keeps homepage changes manageable through Git without adding administrative database operations.
