## **1. Purpose of this document**

Part 01 defined what ForgeSec Academy is.

Part 02 defines exactly what the software must do.

We are moving from product vision to functional requirements. Every feature will receive:

- A unique feature ID.
- A description and purpose.
- User permissions.
- Expected system behavior.
- Inputs and outputs.
- Validation rules.
- Error handling.
- Dependencies.
- Implementation priority.

| Priority | Meaning                                       |
| -------- | --------------------------------------------- |

# **2. System users and roles**

Before defining functionality, we need to establish who can interact with the application.

## **2.1 User roles**

**Guest**

Public

- Browse public tutorials.
- Read write-ups.
- Explore learning paths.
- Search educational content.
- View instructor profiles.
- Attempt publicly available quizzes.

  **Student**

  Authenticated
- Access all public content.
- Maintain personal learning progress.
- Bookmark lessons.
- Maintain learning history.
- Take quizzes with recorded results.
- View personal dashboard.
- Participate in discussions when enabled.

  **Instructor**

  Content contributor
- Create and maintain assigned educational content.
- Manage their own drafts.
- View lesson engagement information where authorized.
- Respond to student questions.
- Update their instructor profile.

  **Administrator**

  Privileged
- Manage users and roles.
- Manage educational content and publication.
- Manage learning paths.
- Manage quizzes and assignments.
- Moderate discussions.
- Configure platform settings.
- Review platform activity.

### **2.2 Role restrictions**

1. Guests cannot access private student information.
2. Students cannot modify another student's progress.
3. Instructors cannot grant themselves administrator permissions.
4. Instructors cannot modify content belonging to other instructors unless explicitly authorized.
5. Administrators have full application-management privileges.
6. Privileged operations must be authorized on the server, not merely hidden in the UI.

**Technical requirement:** Supabase Row Level Security (RLS) must enforce database-level access restrictions.

# **5. FR-02 — Educational Content System**

P0 — Mandatory

**Purpose:** Provide a structured system for publishing, organizing, and displaying educational material.

This is the heart of ForgeSec Academy.

## **5.1 Supported content types**

| Type            | Description                                 |
| --------------- | ------------------------------------------- |
| Tutorial        | Structured technical lesson                 |
| Article         | Educational explanation                     |
| Write-up        | Technical walkthrough or research           |
| Practical guide | Step-by-step instructions                   |
| Reference       | Commands, tools and technical documentation |
| Glossary entry  | Definition of a technical term              |

## **5.2 Content structure**

Each tutorial must support:

- Title.
- Unique slug.
- Short description.
- Main content.
- Category.
- Subcategory.
- Author.
- Difficulty level.
- Estimated reading time.
- Tags.
- Featured image (optional).
- Publication status.
- Publication date.
- Last updated date.
- Related content.

### **Difficulty levels**

1. Beginner.
2. Intermediate.
3. Advanced.

### **Publication statuses**

- Draft.
- Published.
- Archived.

## **5.3 Content behavior**

The system must:

1. Display content according to its type.
2. Display relevant metadata.
3. Support code blocks.
4. Support syntax highlighting.
5. Support headings, tables, images and lists.
6. Support internal links to other lessons.
7. Display related educational content.
8. Generate a table of contents from headings.
9. Display the author's information.
10. Support revision and update dates.

## **5.4 Content authoring decision**

We need to preserve the free-tier architecture.

Therefore, the initial content source will be version-controlled MDX files in the Git repository.

The publishing workflow will be:

**Instructor / Administrator**

Creates or edits educational material

**MDX content**

Stored in the Git repository

**Next.js build**

Validates and generates pages

**Published educational content**

Available to students and visitors

An important scope decision: the initial administrator interface will manage application records, users, quizzes and learning paths. Full browser-based MDX editing and Git publishing will be a later enhancement, not a requirement for launch.

This avoids building a complex CMS unnecessarily.

### **5.5 Acceptance criteria**

- Every published tutorial has a valid URL.
- Draft content is not publicly accessible.
- Code blocks render correctly.
- Content metadata is displayed.
- Related lessons work.
- Content can be updated through version control.
- Archived content is handled appropriately.

**Dependency:** FR-01.

P0 — Mandatory

**Purpose:** Help visitors find relevant educational material quickly.

### **7.1 Searchable content**

- Articles.
- Write-ups.

### **7.2 Required functionality**

| ID        | Requirement                      |
| --------- | -------------------------------- |
| FR-04-001 | Search by title                  |
| FR-04-002 | Search by keywords               |
| FR-04-003 | Search by tags                   |
| FR-04-004 | Filter by category               |
| FR-04-005 | Filter by difficulty             |
| FR-04-006 | Display relevant results         |
| FR-04-007 | Display an empty-results message |

### **7.3 Search behavior**

- Search should be case-insensitive.
- Only published public content should appear.
- Results should display title, description, category and content type.
- Search should not require authentication.
- Search results should support pagination or controlled result limits.

### **7.4 Technical direction**

For the initial content volume, we do not need Elasticsearch, Algolia, or another paid search service.

We can implement search using a generated static search index or a lightweight client-side search library.

The educational content already exists in the repository, so we can generate the search index during the build process.

**Analogy:** A library does not need a separate database server just to locate books when it has a well-organized catalog.

### **7.5 Acceptance criteria**

- Search returns relevant content.
- Filters work correctly.
- Unpublished content never appears.
- Search works for guests.
- Empty results are handled gracefully.

**Dependency:** FR-02.

- Password.

Optional information:

- Short biography.
- Learning interests.

### **8.3 Authentication behavior**

1. A student submits registration information.
2. The system validates the information.
3. Supabase Auth creates the authentication identity.
4. Email verification is handled where configured.
5. A corresponding student profile is created.
6. The student can log in.
7. The system establishes a secure session.
8. The student is redirected to the appropriate destination.

### **8.4 Security requirements**

- Passwords must be managed by Supabase Auth.
- Never store plaintext passwords.
- Use secure session cookies through the Supabase SSR integration.
- Protect private routes.
- Validate authorization on the server.
- Rate-limit sensitive authentication operations where applicable.
- Never trust role information supplied by the browser.

### **8.5 Acceptance criteria**

- Registration works.
- Login works.
- Logout invalidates the session.
- Password reset works.
- Email verification works when enabled.

# **10. FR-07 — Learning Progress Tracking**

P0 — Mandatory

**Purpose:** Track student progress across lessons and learning paths.

This is an important feature because it transforms ForgeSec from a content website into a learning platform.

### **10.1 Required functionality**

| ID        | Requirement                          |
| --------- | ------------------------------------ |
| FR-07-001 | Mark lesson as completed             |
| FR-07-002 | Undo completion                      |
| FR-07-003 | Retrieve completed lessons           |
| FR-07-004 | Calculate learning path progress     |
| FR-07-005 | Store completion timestamp           |
| FR-07-006 | Track recently visited lessons       |
| FR-07-007 | Continue from last incomplete lesson |

### **10.2 Completion rules**

A lesson is completed when the student explicitly marks it complete.

We should not automatically mark a lesson complete merely because someone opened it.

For example:

- Learning path contains 10 lessons.
- Student completes 4 lessons.
- Completion percentage = 40%.

\\[ \text{Progress} = \frac{\text{Completed lessons}}{\text{Total published lessons}} \times 100 \\]

### **10.3 Progress behavior**

- Students can mark lessons complete.
- Students can undo completion.
- Completion status must persist between sessions.
- Progress must be calculated from the student's own records.
- Changes must be reflected in the dashboard.
- Archived or unpublished lessons should not produce misleading progress calculations.

### **10.4 Acceptance criteria**

- Completion status persists.
- Progress calculation is correct.
- Duplicate completion records are prevented.
- Students cannot modify another student's progress.
- Unmarking a lesson recalculates progress correctly.

**Dependencies:** FR-03 and FR-05.

3. Multiple-select questions.

### **11.2 Quiz configuration**

Each quiz should support:

| Field              | Description                 |
| ------------------ | --------------------------- |
| Title              | Quiz name                   |

| Related lesson     | Optional lesson association |
| Questions          | Ordered question collection |
| Passing score      | Minimum passing percentage  |
| Time limit         | Optional                    |
| Attempts allowed   | Configurable limit          |
| Publication status | Draft / Published           |

### **11.3 Quiz behavior**

1. Student opens a quiz.
2. System displays instructions.
3. Student answers questions.
4. Student submits the quiz.
5. System evaluates objective questions.
6. System calculates the score.
7. System displays feedback.
8. System records the attempt for authenticated students.

### **11.4 Feedback**

A useful assessment should explain why an answer is correct or incorrect.

Example:

**Question:** Which Linux command displays the current working directory?

- A. `ls`
- B. `pwd`
- C. `cd`
- D. `mkdir`

Correct answer: `pwd`.

Explanation: `pwd` prints the path of the current working directory.

### **11.5 Acceptance criteria**

- Questions are displayed correctly.
- Answers are validated.
- Scores are calculated correctly.
- Feedback is displayed.

# **12. FR-09 — Practical Assignments**

P1 — Important

**Purpose:** Connect theoretical knowledge with practical execution.

There is no requirement for a simulator, hosted VM, or command execution service.

Students perform exercises on their own computers or authorized servers.

### **12.1 Assignment structure**

Each assignment must support:

- Title.
- Description.
- Related lesson.
- Learning objective.
- Difficulty.
- Required tools.
- Prerequisites.
- Instructions.
- Expected result.
- Verification procedure.
- Safety warnings where appropriate.
- Reference material.

### **12.2 Example assignment**

Beginner

**Assignment: Inspect Linux File Permissions**

**Objective:** Understand Linux file permissions.

**Task:**

1. Create a test file.
2. Inspect its permissions using `ls -l`.
3. Change its permissions using `chmod`.
4. Inspect the permissions again.
5. Explain what changed.

**Verification:**

Students should be able to identify the owner, group, and permission bits.

**Expected learning outcome:** Understand how Linux controls file access.

### **12.3 Submission functionality**

For the initial implementation, I recommend:

- Students can view assignments without registering.
- Registered students can mark assignments as completed.
- Students can optionally submit a text-based explanation.
- Students can optionally provide a link to external evidence.
- Instructors can review submissions in a later enhancement.

We should not initially support large file uploads or screenshot storage. They consume storage and introduce additional moderation and security requirements.

### **12.4 Acceptance criteria**

- Assignments are associated with lessons.
- Instructions are readable.
- Safety warnings are displayed.
- Students can record completion.
- Completion is associated with the correct student.
- No server-side command execution occurs.

**Dependencies:** FR-02 and FR-05.

### **13.6 Content management boundaries**

We need to distinguish between two kinds of content management.

| Content                | Initial management method                             |
| ---------------------- | ----------------------------------------------------- |
| Tutorials              | MDX in Git                                            |
| Articles               | MDX in Git                                            |
| Write-ups              | MDX in Git                                            |
| Glossary               | MDX in Git                                            |
| Learning path metadata | Admin panel / structured data                         |
| Quiz questions         | Admin panel                                           |
| Assignments            | Admin panel or repository, depending on content model |
| Student information    | Admin panel                                           |
| Platform configuration | Admin panel                                           |

This is a deliberate trade-off.

We will not build a sophisticated rich-text CMS just to edit educational articles. Git-based publishing gives us revision history, reliable backups and a simpler architecture.

- Secret management through environment variables.
- No service-role keys in client bundles.
- Appropriate rate limiting.
