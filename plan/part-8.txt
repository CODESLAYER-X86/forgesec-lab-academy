Part 08 — Learning Management System (LMS)
Student Dashboard, Learning Progress, Bookmarks & Learning History
Objective: Build the core learning experience of FORGESEC ACADEMY.

The LMS connects three things already designed:
1. Educational content stored in Git using MDX.
2. Student identities and activity stored in Supabase PostgreSQL.
3. Authentication and permissions from Part 07.
The central principle is simple: students should always know what to learn next, where they stopped, and how much they have completed.

No hosted labs, virtual machines, command execution or expensive learning infrastructure are required.

1. LMS architecture
The LMS should be a module inside the Next.js application, not a separate application or microservice.
Student Interface

The important architectural decision is that the LMS does not store copies of MDX lesson content in PostgreSQL.

Git remains the content source of truth.

Enrollment model
For the initial release, use implicit enrollment.

That means:
- Students can open any published path.
- Students can start any lesson.
- Progress is recorded when they complete lessons.
- A path becomes active when the student starts or completes one of its lessons.
- No separate enrollment approval or enrollment table is necessary.
This avoids unnecessary database complexity.

Think of a learning path like a textbook: owning the book doesn't require formal enrollment. A learner simply starts reading and their progress is tracked.

Important rule
Opening a lesson does not mean completing it.

Completion should be an explicit action.

When a student clicks Mark Complete:
- Create a completion record.
- Store completed_at.
- Update the interface.
- Recalculate affected learning path progress.
- Allow the student to undo completion if necessary.
Use an upsert or equivalent safe operation to prevent duplicate records.
How to calculate progress
Suppose a learning path contains 12 lessons.

The student has completed 4.
\[
\text{Progress} = \frac{4}{12}\times100 = 33.33\%
\]

The percentage should be calculated from:
- The published path's lesson IDs.
- The current user's completed lesson IDs.
Do not store a separate progress percentage in PostgreSQL. It is derived information and could become inconsistent when a learning path changes.
Example
function calculateProgress(
  totalLessons: number,
  completedLessons: number
): number {
  if (totalLessons === 0) return 0;

  return Math.round(
    (completedLessons / totalLessons) * 100
  );
}


This is a simple calculation, but the application must ensure that completed lesson IDs belong to the actual path before counting them.
What happens when content changes?
If a lesson is removed from a learning path:
- It should no longer count toward that path's progress.
- Its historical completion record can remain.
- A lesson reused in another path should retain its completion status.
Use stable lesson IDs. Do not casually rename or recycle them.

6. Continue Learning logic
The Continue Learning button should be intelligent.

It should not simply open the last page a student visited.
Recommended algorithm
1. Identify the student's active learning path.
2. Load the path's ordered lesson IDs.
3. Load the student's completed lesson IDs.
4. Find the first incomplete lesson in the path.
5. Open that lesson.
Example:
Lesson	Status
Introduction	Completed
Terminal Basics	Completed
Filesystem	Completed
File Management	Completed
Permissions	Next lesson
Users and Groups	Not started

The next lesson is Permissions.

If all lessons are completed, display a completion message and suggest another learning path.
Multiple active paths
A student may be studying Linux and Networking simultaneously.

For the initial version:
- Store recent activity.
- Show active paths ordered by most recent activity.
- Let the student choose which path to continue.
- Use the most recently active path for the primary Continue Learning action.
Do not invent a complicated recommendation engine.

8. Learning history
Bookmarks and learning history solve different problems.
- Bookmarks mean: "I want to save this."
- History means: "I visited this."
Use the content_activity table from Part 06.
content_activity
-------------------------
id
user_id
content_id
content_type
last_viewed_at
view_count


Recommended behavior
Whenever an authenticated student opens educational content:
1. Validate the content identity.
2. Upsert the activity record.
3. Update last_viewed_at.
4. Increment view_count.
Use a server-side operation, and avoid making multiple requests for the same page view.
Why not create a row for every page view?
Imagine 10,000 students opening the same lesson 20 times.

An event-per-view design would create 200,000 records.

A single activity record per student and content item can instead maintain the latest visit and visit count.

For this Academy's initial requirements, that is sufficient.

Do not build a full analytics event pipeline yet.

10. Database queries and performance
The LMS should be lightweight and avoid unnecessary database calls.
Dashboard data requirements
Data	Source
User display name	profiles
User roles	user_roles
Completed lessons	lesson_progress
Active learning paths	Git path definitions + activity/progress
Bookmarks	bookmarks
Recent history	content_activity
Quiz results	quiz_attempts

Important optimization rules
1. Fetch dashboard information in a small number of server-side queries.
2. Select only necessary columns.
3. Use pagination for bookmarks and history.
4. Avoid fetching every lesson body just to calculate progress.
5. Generate static content indexes at build time.
6. Do not query PostgreSQL for public lesson content.
7. Avoid recalculating identical path progress repeatedly within one request.
8. Never share user-specific cached data across sessions.
Recommended caching
Data	Caching approach
Public MDX lessons	Static/build-time caching
Learning path definitions	Static/build-time caching
Student progress	Request-specific or carefully user-scoped
Bookmarks	Request-specific
Learning history	Request-specific
User profile	Request-specific or safely scoped

A useful analogy: public lessons are like library books available to everyone, so they can be cached broadly. Student progress is like an individual library account, so it must remain private.

Responsibilities
- Schemas: Validate incoming data using Zod.
- Services: Implement learning rules and progress calculations.
- Repositories: Communicate with PostgreSQL.
- Actions: Handle authenticated user interactions.
- Components: Display the learning experience.
- Types: Define shared TypeScript interfaces.
Keep the business logic independent of React components so it can be tested and reused.

What should NOT be built yet
- AI learning recommendations.
- Gamification points and leaderboards.
- Real-time learning analytics.
- Social learning feeds.
- Live classrooms.
- Hosted terminal environments.
- Automated student command execution.
- Complex enrollment workflows.
These features add engineering and maintenance costs without being necessary for the Academy's initial value proposition.

Part 08 — Final architectural decisions
Area	Decision
LMS architecture	Internal Next.js module
Learning path source	Git/YAML
Lesson content	Git/MDX
Progress storage	PostgreSQL
Enrollment	Implicit
Completion	Explicit student action
Progress calculation	Derived from lesson IDs
Continue Learning	First incomplete lesson in most recently active path
Bookmarks	PostgreSQL
Learning history	One activity record per user/content
Dashboard	Server-rendered, user-specific
Public lessons	Static generation where practical
Hosted labs	Not included

The most important design decision: keep the learning content independent from student activity. Git controls what is taught; PostgreSQL tracks how each student interacts with it.

That separation will make content updates, database maintenance and future expansion much easier.
