# **Part 09 — Assessment System**

## **Quizzes, Question Management, Scoring, Attempts & Results**

**Objective:** Build a lightweight assessment system that helps students measure their understanding of FORGESEC ACADEMY's educational content.

The assessment system should support knowledge checks without turning the Academy into an expensive examination platform.

It will use:

- Next.js + TypeScript for application logic.
- Supabase PostgreSQL for questions, answers and results.
- Supabase Auth for student identity.
- Server-side scoring to protect correct answers.
- Git/MDX content to provide educational explanations and references.

**Core principle:** A quiz should measure understanding, not simply reward students for clicking through lessons.

## **1. Assessment system architecture**

The assessment system will be an internal module of the existing Next.js application.

**Student Interface**

Quiz instructions · Questions · Answers · Results

**Next.js Assessment Module**

Validation · Attempt management · Scoring · Authorization

**Supabase PostgreSQL**

Quizzes · Questions · Options · Answer keys · Attempts · Results

### **Responsibilities**

| Component          | Responsibility                          |
| ------------------ | --------------------------------------- |
| Quiz interface     | Display questions and collect answers   |
| Assessment service | Manage quiz rules and scoring           |
| Database           | Store quiz configuration and results    |
| Admin interface    | Create and manage quizzes               |
| RLS                | Protect student records and answer keys |

The quiz engine must never trust scores calculated by the browser.

### **Why only three initially?**

They cover most beginner and intermediate knowledge checks.

Do not immediately introduce:

- Drag-and-drop questions.
- Matching questions.
- Essay grading.
- Code execution questions.
- Complex adaptive examinations.

Those features would increase development and testing requirements.

Later, short-answer questions could be introduced with manual instructor evaluation.

## **3. Quiz structure and configuration**

Each quiz should have:

| Field               | Purpose                              |
| ------------------- | ------------------------------------ |
| Title               | Quiz name                            |
| Slug                | Unique URL                           |
| Description         | What the quiz evaluates              |
| Related lesson/path | Educational context                  |
| Difficulty          | Beginner, intermediate or advanced   |
| Passing score       | Required percentage                  |
| Attempt limit       | Maximum submissions                  |
| Status              | Draft, published or archived         |
| Questions           | Ordered question collection          |
| Created by          | Responsible administrator/instructor |

The `quizzes` table from Part 06 already provides most of this structure.

I recommend adding a few optional configuration fields through a migration:

```
time_limit_seconds
randomize_questions
randomize_options
show_explanations
allow_guest_attempts
```

Use conservative defaults:

| Setting             | Initial default                              |
| ------------------- | -------------------------------------------- |
| Time limit          | No limit                                     |
| Randomize questions | No                                           |
| Randomize options   | No                                           |
| Show explanations   | Yes, after submission                        |
| Guest attempts      | Yes                                          |
| Attempt limit       | 3 for formal quizzes; unlimited for practice |

These should be configurable per quiz rather than hardcoded globally.

## **5. Database architecture**

Part 06 already defined the required assessment tables.

The relationships are:

**quizzes**

**quiz_questions**

**quiz_options**

**quiz_answer_keys**

**quiz_attempts**

**quiz_attempt_answers**

Simplified relationship overview. Questions belong to quizzes; attempts belong to users and quizzes.

### **Table responsibilities**

| Table                  | Stores                                     |
| ---------------------- | ------------------------------------------ |
| `quizzes`              | Quiz configuration                         |
| `quiz_questions`       | Question text, type, points and order      |
| `quiz_options`         | Available answers                          |
| `quiz_answer_keys`     | Correct answers and explanations           |
| `quiz_attempts`        | Student attempt and final score            |
| `quiz_attempt_answers` | Answers submitted for individual questions |

### **Important design improvement: quiz versioning**

There is one issue worth addressing before implementation.

Suppose a student completes a quiz today. Next month, an instructor changes two questions and modifies the correct answers.

Should the student's historical result be evaluated against the old quiz or the new quiz?

It should preserve the version the student actually attempted.

I recommend introducing:

- `version` on the quiz.
- A quiz version snapshot or immutable published question set.
- `quiz_version` on `quiz_attempts`.

When a published quiz changes, create a new version rather than silently modifying the version associated with historical attempts.

This is especially important if the Academy eventually issues certificates based on assessment performance.

For the first release, the simplest implementation is to lock published quiz versions and create a new version whenever questions change.

### **Attempt states**

The existing `quiz_attempts` table should be extended with an explicit status:

| Status        | Meaning                   |
| ------------- | ------------------------- |
| `in_progress` | Student has started       |
| `submitted`   | Student submitted answers |
| `expired`     | Time limit expired        |
| `abandoned`   | Attempt was abandoned     |

Do not treat an unfinished attempt as a completed quiz result.

### **Attempt restrictions**

Before creating an attempt, verify:

1. The quiz is published.
2. The user is allowed to access it.
3. The attempt limit has not been reached.
4. The quiz is still accepting attempts.
5. The current quiz version is valid.

For guest attempts, keep the score in the temporary response rather than persisting identifiable student records. If you later need guest analytics, design a separate privacy-conscious anonymous attempt mechanism.

## **7. Server-side scoring**

This is the most security-sensitive part of the assessment system.

**Never send the correct answer keys to the browser before the student submits the quiz.**

Imagine giving students an examination paper with the answer sheet printed on the back. That is what exposing answer keys through the API would do.

### **Scoring example**

Suppose a quiz contains:

| Question | Points | Student result |
| -------- | ------ | -------------- |
| Q1       | 2      | Correct        |
| Q2       | 2      | Incorrect      |
| Q3       | 3      | Correct        |
| Q4       | 3      | Correct        |
| Q5       | 2      | Incorrect      |

Total possible points:

\\[ 2+2+3+3+2=12 \\]

Earned points:

\\[ 2+0+3+3+0=8 \\]

Final percentage:

\\[ \frac{8}{12}\times100=66.67\\% \\]

If the passing threshold is 70%, the student does not pass.

### **Scoring rules**

For single-choice and true/false:

- Correct answer: full points.
- Incorrect answer: zero points.

For multiple-select, I recommend exact-set matching initially:

- All correct options selected.
- No incorrect options selected.
- Full points awarded.
- Otherwise, zero points.

Partial credit can be added later, but it introduces more complex scoring and explanation requirements.

### **Server-side implementation concept**

```
type QuestionResult = {
  questionId: string;
  selectedOptionIds: string[];
  correctOptionIds: string[];
  points: number;
};

function isCorrect(result: QuestionResult): boolean {
  const selected = [...result.selectedOptionIds].sort();
  const correct = [...result.correctOptionIds].sort();

  return (
    selected.length === correct.length &&
    selected.every((id, index) => id === correct[index])
  );
}
```

This is only the comparison logic. In production:

- Retrieve answer keys on the server.
- Verify every selected option belongs to its question.
- Reject duplicate option IDs.
- Reject answers for questions outside the attempt's quiz version.
- Calculate the score server-side.
- Persist the attempt and answers atomically.
- Prevent the same attempt from being submitted twice.

A database transaction or trusted database function should handle the final submission so a partial write cannot leave an inconsistent result.

## **9. Guest versus registered assessments**

I recommend supporting both.

| Feature                | Guest | Registered student |
| ---------------------- | ----- | ------------------ |
| View published quiz    | Yes   | Yes                |
| Attempt quiz           | Yes   | Yes                |
| Receive score          | Yes   | Yes                |
| View explanations      | Yes   | Yes                |
| Save attempt history   | No    | Yes                |
| View previous attempts | No    | Yes                |
| Dashboard integration  | No    | Yes                |

### **Why allow guest attempts?**

A visitor should be able to evaluate the quality of the Academy without first creating an account.

For example, someone might discover a Linux tutorial through Google and want to test their understanding immediately.

Do not force registration before allowing a basic knowledge check.

After a guest finishes, you can offer account registration to save future progress, but do not imply that their anonymous result will automatically transfer unless that functionality is implemented.

### **Publishing validation**

A quiz cannot be published unless:

- It has at least one question.
- Every question has valid answer options.
- Every question has at least one valid correct answer.
- Single-choice questions have exactly one correct answer.
- True/false questions have the expected two choices.
- Points are positive.
- Passing score is valid.
- All question positions are unique.

Once published, the question set should be immutable for that version.

## **11. Security and authorization**

The quiz system must follow the security architecture from Parts 06 and 07.

| Resource                 | Student access                 |
| ------------------------ | ------------------------------ |
| Published quizzes        | Read                           |
| Draft quizzes            | No access                      |
| Published questions      | Read without answer keys       |
| Answer keys              | No direct access               |
| Own attempts             | Read                           |
| Other students' attempts | No access                      |
| Own submitted answers    | Read, subject to result policy |
| Quiz scoring operation   | Server-controlled              |

### **Important security controls**

1. Enable RLS on all assessment tables.
2. Do not expose `quiz_answer_keys` through client-accessible queries.
3. Do not accept client-calculated scores.
4. Do not allow direct student writes to final score fields.
5. Derive the user ID from the verified session.
6. Validate question and option IDs server-side.
7. Apply rate limits to quiz creation and submission operations.
8. Prevent duplicate submissions.
9. Keep administrative answer-key operations server-only.
10. Write administrative publication and modification events to `admin_audit_logs`.

### **Additional issue: question randomization**

If you enable question randomization, store the question ordering for each attempt. Otherwise, a student may refresh and receive a different question sequence.

The same applies to randomized answer options.

For the first release, keep randomization disabled.

### **Features to postpone**

- AI-generated questions.
- Adaptive examinations.
- Proctoring.
- Webcam monitoring.
- Anti-cheat surveillance.
- Automated code execution.
- Competitive leaderboards.
- Complex examination scheduling.

For a free educational Academy, these features are unnecessary and would create privacy, security and maintenance burdens.

## **Part 09 — Final architectural decisions**

| Area                    | Decision                                   |
| ----------------------- | ------------------------------------------ |
| Assessment architecture | Internal Next.js module                    |
| Question types          | Single choice, multiple select, true/false |
| Question storage        | PostgreSQL                                 |
| Answer-key storage      | Restricted PostgreSQL table                |
| Scoring                 | Server-side                                |
| Multiple-select scoring | Exact-set matching                         |
| Guest attempts          | Supported                                  |
| Student attempt history | Persisted                                  |
| Attempt limits          | Configurable                               |
| Quiz versions           | Immutable published versions               |
| Explanations            | Display after submission                   |
| Randomization           | Disabled initially                         |
| Advanced assessments    | Future development                         |

**My recommendation:** Make quizzes short and directly related to lessons. A five-question knowledge check with good explanations is more useful for beginners than a 50-question examination with no meaningful feedback.
