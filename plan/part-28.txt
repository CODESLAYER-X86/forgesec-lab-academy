Part 28 — Admin Panel Implementation
Objective: Build the FORGESEC ACADEMY administration interface for managing users, instructor permissions, quizzes, assignments, submissions and audit logs.

The admin panel must use the permanent ADMIN_EMAILS authorization system established in Part 27.

Architecture: Next.js Server Components + Server Actions + Supabase PostgreSQL. No separate admin backend, no Express server and no full CMS.

4. User management
Route:
/admin/users


Administrators should be able to:
- Search users by display name or email.
- Filter by role.
- View registration date.
- View account status.
- Open individual user details.
- Promote a student to instructor.
- Remove instructor privileges.
- Suspend or reactivate accounts, if account suspension is implemented.
Suggested table:
User	Role	Joined	Status
Student A	Student	Date	Active
Instructor B	Instructor	Date	Active
Student C	Student	Date	Active

Use pagination rather than loading every user.
Individual user details
Route:
/admin/users/[userId]


Display:
- Profile information.
- Google account email.
- Current role.
- Registration date.
- Learning progress summary.
- Quiz performance summary.
- Assignment completion summary.
- Administrative actions.
Do not expose OAuth tokens, session information or unnecessary personal data.
User role changes
When an administrator promotes a student:
1. Verify administrator identity.
2. Validate the target user ID.
3. Check the target account exists.
4. Confirm the requested role.
5. Update user_roles.
6. Record the change in admin_audit_logs.
7. Return a success response.
Use a database transaction or trusted database function so the role update and audit record succeed or fail together.

Never let a student edit their own role.

Important: The environment-based admin allowlist takes precedence. A person removed from ADMIN_EMAILS must not retain administrator access merely because of a database role record.

Available actions:

- Revoke permission.
- Inspect permission history.
Use explicit permission identifiers, such as:

quiz.edit_own
assignment.create
assignment.edit_own

Do not build a complicated drag-and-drop permission editor. A straightforward table with controlled switches is sufficient.

8. Submission management
Route:
/admin/submissions


This is a future-ready module, not a mandatory first-release feature.

When evidence submissions become available, authorized instructors should be able to:
- View assigned student submissions.
- Review evidence.
- Approve completion.
- Request corrections.
- Add feedback.
Students should only access their own submissions.

For version 1.0, keep assignment completion self-reported. Do not introduce file uploads merely to populate this page.
9. Audit logs
Route:
/admin/audit-logs


This page is essential because administrative actions can affect the entire platform.

Display:
Field	Example
Actor	Administrator
Action	admin.user.role_changed
Target	User UUID
Timestamp	Date and time
Details	Student → Instructor

Filters:
- Action type.
- Actor.
- Target.
- Date range.
Audit logs should be read-only from the admin interface.

Never provide a button to edit or delete historical audit events.

Do not record secrets or session credentials.

12. User suspension and account deletion
These are separate operations.

Suspension:
- Prevent new application access.
- Revoke or invalidate active sessions where supported.
- Preserve learning history and audit records.
- Record who suspended the account and why.
A profiles.account_status field or dedicated account status table can be introduced when suspension is implemented. Enforce suspension on the server and in database policies; hiding the interface alone is insufficient.

Deletion:
- Follow the account deletion and retention policy from Part 23.
- Use a trusted server-side process.
- Delete or anonymize relevant records according to policy.
- Preserve required audit history without retaining unnecessary personal information.
Do not implement permanent deletion as a casual one-click user-table action.
13. Admin security requirements
Threat	Protection
Student opens admin URL	requireAdmin()
Forged Server Action request	Independent server authorization
Role manipulation	Restricted database permissions
Admin email spoofing	Verified OAuth identity
Unauthorized database access	RLS and server-only privileged client
Audit tampering	Append-only database permissions
Accidental last-admin removal	Environment-based admin membership
Cross-user data access	Ownership and authorization checks
Malicious input	Zod validation
Secret exposure	Server-only environment variables
Quiz answer leakage	Separate answer-key access control

Additional safeguards:
- Enable MFA on administrator Google accounts.
- Consider a fresh authentication check for especially sensitive operations.
- Never expose a generic service-role database query endpoint.
- Add rate limiting to sensitive administrative operations where practical.
- Log failed authorization attempts without logging credentials.
14. Performance strategy
The admin panel will be used by relatively few people, so keep its architecture lightweight.
Feature	Strategy
User directory	Server-side pagination
User search	Database filtering
Dashboard	Small aggregate queries
Quiz listing	Pagination
Assignment listing	Pagination
Audit logs	Date filters and pagination
Permissions	Fetch only relevant records
Statistics	Reuse Part 29 metric definitions

Avoid loading all users, all quiz attempts or all audit logs into memory.

Do not build a separate analytics service.
