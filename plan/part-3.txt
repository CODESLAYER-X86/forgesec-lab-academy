# **FORGESEC ACADEMY**

## **Part 03 — Student Experience, Learning Workflows & Navigation Architecture**

Planning document 03/14

UX / Product workflows

Student journey

## **1. Purpose of this document**

Part 01 defined the product vision.

Part 02 defined the software functionality.

Part 03 defines how students will actually use ForgeSec Academy.

We need to answer several important questions:

- What does a visitor see when opening the website?
- How does someone discover a suitable learning path?
- How does a student navigate lessons?
- How do practical assignments fit into the learning experience?
- How does the platform remember learning progress?
- What happens when a student returns after several days?
- How should the experience differ between guests and registered students?

The objective is to create a learning experience that is simple, predictable, and engaging without making the website unnecessarily complicated.

**Core UX principle: Students should spend their time learning cybersecurity, not figuring out how to use the platform.**

# **2. Target student experience**

We should design the platform around three primary user journeys.

Journey A

**First-time visitor**

Discovers ForgeSec Academy, explores educational content, and starts learning without registration.

Journey B

**Registered student**

Creates an account, follows learning paths, tracks progress, saves lessons and takes quizzes.

Journey C

**Returning student**

Opens the dashboard, resumes learning, completes assignments and reviews previous topics.

These journeys should work independently. A visitor must not be forced to register before discovering the quality of the educational material.

# **4. Journey B — Student registration and onboarding**

## **4.1 Registration experience**

Registration should be short.

Required fields:

- Display name.
- Email address.
- Password.

Optional:

- Profile picture.
- Learning interests.

We should not create a lengthy registration questionnaire.

### **4.2 First-login experience**

After registration and authentication, the student should enter a simple onboarding experience.

Recommended steps:

1. Welcome the student.
2. Briefly explain how ForgeSec Academy works.
3. Recommend a beginner learning path.
4. Provide an option to explore other subjects.
5. Take the student to the dashboard.

Onboarding must be skippable.

### **4.3 Learning interest selection**

We can optionally let students select interests such as:

- Linux.
- Networking.
- Web security.
- Penetration testing.
- Digital forensics.
- Defensive security.
- Security programming.

These selections can be used for recommendations later.

They should not restrict access to other content.

### **4.4 Acceptance criteria**

- Registration takes only a few steps.
- Onboarding is optional.
- Students can skip interest selection.
- Students can access all public learning materials.
- A student's initial dashboard contains useful recommendations.

- Estimated duration.

### **6.2 Learning path navigation**

Students should be able to:

- View the entire curriculum.
- Open any published lesson.
- Understand lesson ordering.
- Identify completed lessons.
- Identify the current next lesson.
- See the overall progress when authenticated.

The default should be recommended ordering, not artificial locking.

A completed path should remain accessible for revision.

- Completed lesson indicators.

Main content

**Educational material**

- Lesson title.

Right sidebar

Every lesson should display:

- Learning path.
- Lesson title.
- Short description.
- Difficulty level.
- Estimated reading time.

- Last updated date.

## **7.3 Reading controls**

Recommended controls:

| Control           | Function                            |
| ----------------- | ----------------------------------- |
| Table of contents | Jump to a heading                   |
| Copy code         | Copy code blocks                    |
| Bookmark          | Save lesson                         |
| Mark complete     | Record completion                   |
| Previous lesson   | Navigate backward                   |
| Next lesson       | Navigate forward                    |
| Share             | Copy lesson URL                     |
| Report issue      | Report inaccurate or broken content |

We should avoid adding too many controls around the reading area.

## **7.4 Code block experience**

Code examples are particularly important for cybersecurity education.

A code block should support:

- Syntax highlighting.
- Copy-to-clipboard.
- Language identification.
- Optional command descriptions.
- Optional expected output.
- Optional warnings.

Example:

**Bash**

Terminal command

```
pwd
ls -lah
whoami
```

Example commands for inspecting the current Linux environment.

For potentially destructive commands, the lesson should explain their effects before presenting them.

## **7.5 Lesson completion behavior**

At the end of a lesson:

1. Display a short summary.
2. Display the practical assignment if available.
3. Display a knowledge check if available.
4. Provide a Mark as Complete action.
5. Display Previous and Next navigation.
6. Suggest related material.

Completion should be explicit and reversible.

## **7.6 Reading preferences**

Useful future enhancements:

- Light and dark reading themes.
- Font-size adjustment.
- Reading-width adjustment.
- Copy code blocks.
- Bookmark sections or lessons.

I would prioritize copy buttons and responsive reading over extensive customization.

# **8. Practical assignment experience**

We have already decided that students will execute tasks on their own environments.

The platform should make that experience understandable.

## **8.1 Assignment page structure**

Practical assignment

**Configure and inspect an SSH service**

**Objective**

Understand how an SSH service is configured and how its status can be verified.

**Requirements**

- Linux environment.
- OpenSSH installed.
- An authorized machine on which to practice.

**Instructions**

1. Inspect the SSH service status.
2. Review its configuration.
3. Identify the listening port.
4. Verify connectivity from an authorized client.

**Expected result**

You should understand how to inspect SSH service status, configuration and connectivity.

**Completion**

The student performs the work independently.

Assignment status

Not completed

Illustrative example, not an instruction to expose SSH to the public internet.

## **8.2 Assignment states**

| State       | Meaning                                    |
| ----------- | ------------------------------------------ |
| Not started | Student has not marked it complete         |
| In progress | Student has started the task               |
| Completed   | Student marks the task complete            |
| Submitted   | Student has submitted an optional response |
| Reviewed    | Instructor has reviewed a submission       |

For the initial version, Not started, In progress and Completed are sufficient.

## **8.3 Student interaction**

Students should be able to:

- Read the task.
- Review requirements.
- Follow instructions.
- Check expected results.
- Mark the task complete.
- Optionally provide a written explanation if submission is enabled.

The platform must not claim that it verified an actual system configuration when the student simply marked the assignment complete.

That distinction is important for educational credibility.

After submission, display:

- Total questions.
- Correct answers.
- Incorrect answers.

# **10. Bookmark and personal learning experience**

Students should be able to save useful educational material.

## **10.1 Bookmark behavior**

A student can bookmark:

- Tutorials.
- Articles.
- Write-ups.
- Learning paths.
- Reference materials.

The initial implementation should support bookmarking complete content items rather than individual paragraphs.

### **10.2 Bookmark page**

The student's bookmarks page should contain:

- Saved content title.
- Content category.
- Short description.
- Date saved.
- Remove bookmark action.

### **10.3 Personal learning history**

The platform should distinguish between:

- Recently viewed.
- Completed.
- Bookmarked.
- Currently studying.

These are different types of activity.

For example, opening a lesson does not mean completing it.

# **12. Student dashboard workflows**

The dashboard should be the student's central learning workspace.

### **12.1 Dashboard navigation**

I recommend these sections:

| Section      | Purpose                  |
| ------------ | ------------------------ |
| Overview     | Learning summary         |
| My Learning  | Active learning paths    |
| Bookmarks    | Saved content            |
| History      | Recently viewed material |
| Quiz Results | Assessment history       |
| Profile      | Personal information     |
| Settings     | Account preferences      |

### **12.2 Dashboard scenarios**

**Scenario A: New student**

- No completed lessons.
- No bookmarks.
- No quiz attempts.

Display onboarding guidance and suggested beginner content.

**Scenario B: Active student**

- Show ongoing learning paths.
- Show completion progress.
- Show Continue Learning.
- Show recent activity.

**Scenario C: Student who completed a path**

- Show completed learning paths.
- Suggest the next relevant learning path.
- Allow revision of completed material.

### **12.3 Resume learning rules**

When a student selects Continue Learning:

1. Identify active learning paths.
2. Find the next incomplete required lesson.
3. Open that lesson.
4. If all required lessons are complete, show a completed state and recommend the next path.

If a student has multiple active paths, prioritize the path they most recently engaged with.

# **16. Student interaction and notification rules**

We need to define how the application responds to student actions.

| Student action                 | Expected response                |
| ------------------------------ | -------------------------------- |
| Bookmark lesson                | Show confirmation                |
| Complete lesson                | Update progress                  |
| Undo completion                | Recalculate progress             |
| Submit quiz                    | Display result                   |
| Save profile                   | Show success or validation error |
| Remove bookmark                | Update saved list                |
| Login with invalid credentials | Display safe error               |
| Open unavailable lesson        | Display not-found state          |
| Lose internet connection       | Show recoverable error           |

### **Notification principles**

- Use small, non-intrusive notifications.
- Avoid unnecessary popups.
- Do not interrupt lesson reading.
- Require confirmation for destructive operations.
- Never display sensitive information in notifications.

# **17. Accessibility and learning usability**

The platform should be usable by students with different devices and accessibility requirements.

Recommended baseline:

- WCAG 2.2 AA as the accessibility target.
- Semantic HTML.
- Keyboard navigation.
- Visible focus indicators.
- Proper form labels.
- Alternative text for meaningful images.
- Sufficient contrast.
- Accessible quiz controls.
- Reduced-motion support.
- Meaningful error messages.

A particularly important point for technical tutorials: code blocks must remain readable without forcing users to zoom the entire page.

# **19. UX rules and non-negotiable decisions**

The following rules should guide the implementation.

| ID     | Rule                                                                          |
| ------ | ----------------------------------------------------------------------------- |
| UX-001 | Public educational content must not require registration.                     |
| UX-002 | Registration must remain simple.                                              |
| UX-003 | Lessons must be readable on mobile.                                           |
| UX-004 | Students must be able to navigate freely.                                     |
| UX-005 | Viewing a lesson must not automatically mark it complete.                     |
| UX-006 | Learning progress must persist between sessions.                              |
| UX-007 | Continue Learning must identify the next incomplete lesson.                   |
| UX-008 | Assignments must be executable independently by students.                     |
| UX-009 | Quiz feedback must explain incorrect answers.                                 |
| UX-010 | The lesson reading area must remain distraction-free.                         |
| UX-011 | All student-specific information must remain private.                         |
| UX-012 | The interface must remain lightweight.                                        |
| UX-013 | Learning paths should not artificially lock educational content.              |
| UX-014 | The platform must support self-paced learning without requiring live classes. |

The self-paced model is especially important: students should be able to study independently, perform tasks on their own schedules, and return whenever convenient.&#x20;
