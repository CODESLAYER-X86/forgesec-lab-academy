# **Part 20 — Technical Implementation Blueprint: Exact Stack, Dependencies, Configuration & Initial Repository Setup**

**Objective:** Turn the approved FORGESEC ACADEMY 1.0 architecture into an actual development-ready repository.

Parts 01–19 established what we are building. This part establishes the technical foundation: which technologies to use, which packages to install, how to organize the code, and how to configure the project.

My recommendation is to start with a **single Next.js application using TypeScript**, with Supabase handling authentication and persistent data. We will not introduce a separate Express backend, microservices, or a CMS.

## **2. Runtime and project configuration**

- Node.js LTS supported by the selected Next.js release.
- npm as the package manager.
- TypeScript strict mode.
- Next.js App Router.
- React Server Components by default.
- ESLint for code quality.
- Git for version control.

## **3. Package dependencies**

We should avoid installing unnecessary packages.

### **A. Core application dependencies**

```
npm install \
  @supabase/supabase-js \
  @supabase/ssr \
  zod \
  lucide-react \
  clsx \
  tailwind-merge
```

Responsibilities:

| Package                 | Purpose                         |
| ----------------------- | ------------------------------- |
| `@supabase/supabase-js` | Supabase client                 |
| `@supabase/ssr`         | Cookie-based SSR authentication |
| `zod`                   | Validation                      |
| `lucide-react`          | Icons                           |
| `clsx`                  | Conditional CSS classes         |
| `tailwind-merge`        | Merge Tailwind classes safely   |

### **B. Content dependencies**

```
npm install \
  next-mdx-remote \
  gray-matter \
  remark-gfm \
  rehype-pretty-code \
  shiki \
  fast-glob \
  minisearch
```

Responsibilities:

- `next-mdx-remote`: Render MDX content in the App Router.
- `gray-matter`: Read YAML frontmatter.
- `remark-gfm`: Support GitHub-flavored Markdown.
- `rehype-pretty-code` and `shiki`: Highlight technical code blocks.
- `fast-glob`: Discover content files.
- `minisearch`: Search the generated content index.

**Important:** MDX must only come from trusted repository contributors. Never compile arbitrary student-submitted MDX.

Also, keep the rendering pipeline consistent: do not install multiple MDX renderers or syntax highlighters for the same job.

### **C. Development dependencies**

```
npm install -D \
  vitest \
  @vitejs/plugin-react \
  jsdom \
  @testing-library/react \
  @testing-library/user-event \
  @testing-library/jest-dom \
  @playwright/test \
  @axe-core/playwright \
  tsx
```

These provide:

- Unit tests.
- React component tests.
- Browser automation.
- Accessibility checks.
- TypeScript script execution.

Some testing packages may need version-compatible configuration with the selected React and Vite versions.

### **D. Packages to postpone**

Do not install these without a specific requirement:

- Redux or another global state library.
- Socket.IO.
- Prisma or another ORM alongside Supabase's client.
- Elasticsearch.
- Redis.
- BullMQ.
- An analytics warehouse.
- A separate authentication library.
- A full UI component framework.

We already have enough tools to build the initial product.

## **5. Environment configuration**

Create `.env.local`:

```
NEXT_PUBLIC_SITE_URL=http://localhost:3000

NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
```

For the example file, create `.env.example`:

```
NEXT_PUBLIC_SITE_URL=
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
```

These are placeholders. Obtain the actual Supabase URL and publishable key from your project settings.

### **Important security rules**

- `.env.local` must be excluded from Git.
- `.env.example` must contain no real secrets.
- Google OAuth client credentials belong in the appropriate Supabase/provider configuration.
- Never expose a Supabase secret or service-role key through `NEXT_PUBLIC_` variables.
- Do not introduce a privileged service-role client unless a specific operation requires it and has a carefully tested authorization boundary.

For normal student and administrator operations, prefer authenticated, user-scoped Supabase clients combined with RLS.

## **6. Supabase client architecture**

We need separate browser and server clients.

```
src/lib/supabase/
├── client.ts
├── server.ts
└── middleware.ts
```

The third filename is illustrative: its actual implementation should follow the session-refresh convention supported by the selected Next.js version. In newer Next.js conventions, this may be a `proxy.ts` at the project root rather than a middleware module.

### **Browser client**

Used only for browser-side operations that genuinely require it.

### **Server client**

Used in Server Components, Server Actions and Route Handlers.

### **Session refresh**

Responsible for refreshing authentication sessions and updating cookies according to the Supabase SSR integration.

**Important:** Never trust a user ID or role received from a browser. Retrieve the verified identity from the server-side Supabase Auth session.

## 8. TypeScript configuration

Keep strict type checking enabled.

The important settings should include:

```json
{
  "compilerOptions": {
    "strict": true,
    "noEmit": true,
    "esModuleInterop": true,
    "moduleResolution": "bundler",
    "resolveJsonModule": true,
    "isolatedModules": true,
    "jsx": "preserve",
    "incremental": true,
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
````

This is a configuration reference, not a complete replacement for the generated `tsconfig.json`. Preserve the other options required by the installed Next.js version.

Avoid `any` unless there is a justified interoperability requirement.

## **9. Package scripts**

Add these project scripts to `package.json` while preserving the scripts generated by Next.js:

```
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:watch": "vitest",
    "test:e2e": "playwright test",
    "validate-content": "tsx scripts/validate-content.ts",
    "generate-search": "tsx scripts/generate-search-index.ts",
    "check": "npm run lint && npm run typecheck && npm run test && npm run validate-content"
  }
}
```

Do not run `generate-search` as part of every test. Generate the search index when content changes or during the production build, depending on the final content pipeline.

## **11. Development conventions**

These rules should apply to all future development.

| Area              | Convention                                      |
| ----------------- | ----------------------------------------------- |
| Naming            | `kebab-case` files, PascalCase React components |
| Functions         | camelCase                                       |
| Types             | PascalCase                                      |
| Database          | snake_case                                      |
| Validation        | Zod                                             |
| Server logic      | Server Actions or services                      |
| UI                | Server Components by default                    |
| Client components | Only where interaction requires them            |
| Database changes  | Versioned migrations                            |
| Content           | Git-managed MDX/YAML                            |
| Errors            | Structured, sanitized errors                    |
| Tests             | Added with features                             |

### **Example feature module**

```
src/modules/learning/
├── schemas/
│   └── progress.schema.ts
├── services/
│   └── progress.service.ts
├── repositories/
│   └── progress.repository.ts
├── actions/
│   └── update-progress.ts
├── components/
└── types/
```

The separation is intentional:

- Schema validates data.
- Repository handles database access.
- Service implements business logic.
- Action connects the service to the application interface.

A small feature may not need every layer. Don't create abstractions simply to fill directories.
