## **1. Purpose of this document**

Parts 01–03 established the product, functionality and student experience.

Part 04 defines how ForgeSec Academy's educational content will be structured, stored, validated, published and maintained.

This is one of the most important architectural decisions because educational content will eventually become the largest part of the platform.

We need an architecture that:

- Supports hundreds or thousands of lessons.
- Does not require a paid CMS.
- Does not consume Supabase database storage for articles.
- Works with Vercel's free hosting constraints.
- Supports technical code examples and diagrams.
- Allows content revision through Git.
- Integrates cleanly with Next.js and TypeScript.
- Keeps URLs stable.
- Makes content easy to maintain.

### **Core architectural decision**

# **Git-based content architecture**

Recommended baseline

**Educational content:** MDX files in Git.

**Content rendering:** Next.js.

**Metadata validation:** TypeScript schemas.

**Version history:** Git.

**Student records:** Supabase PostgreSQL.

**Deployment:** Vercel.

Educational content will not be stored in Supabase.

Think of Git as the Academy's educational library, Next.js as the library's display system, and Supabase as the student records office.

Each system has a distinct responsibility.

# **2. Educational content taxonomy**

Before defining files, we need to establish what kinds of educational content ForgeSec Academy publishes.

Not everything should be called a tutorial.

# **3. Category and subcategory architecture**

Categories organize educational material across the entire Academy.

Learning paths organize lessons into a sequence.

These two concepts should remain separate.

## **3.1 Proposed initial categories**

**Linux & System Administration**

- Linux Fundamentals
- Shell and Bash
- Filesystem
- Users and Permissions
- Services and Processes
- System Administration

  **Networking**

- Network Troubleshooting

  **Programming & Development**
- Python

  **Security Research & Write-ups**
- CTF Write-ups

These are initial categories, not a requirement to publish every category immediately.

## **3.2 Category metadata**

Each category should have:

- Name.
- Unique slug.
- Description.
- Icon identifier.
- Optional parent category.
- Display order.
- Publication status.

We should avoid hardcoding category information independently in multiple components.

For initial implementation, category definitions can be stored in TypeScript configuration files in Git.

## **3.3 Taxonomy rules**

1. Every content item should have one primary category.
2. Additional categories should only be used when genuinely relevant.
3. Tags should describe narrower subjects.
4. Categories should not duplicate learning paths.
5. Categories should not become excessively deep.
6. URLs should remain stable when display names change.

A practical example:

- Category: Linux & System Administration
- Subcategory: File Permissions
- Tags: `chmod`, `chown`, `permissions`, `linux`

# **4. MDX content format**

We will use MDX as the primary educational content format.

MDX combines Markdown with reusable React components.

This is particularly suitable for technical education because lessons frequently need:

- Code blocks.
- Tables.
- Images.
- Diagrams.
- Warnings.
- Command outputs.
- Interactive elements in the future.

## **4.1 Why MDX instead of HTML?**

| Consideration        | MDX                      | Raw HTML                      |
| -------------------- | ------------------------ | ----------------------------- |
| Readability          | Excellent                | More verbose                  |
| Code examples        | Native Markdown          | Manual markup                 |
| Git revision         | Easy                     | More cumbersome               |
| Reusability          | React components         | Requires additional structure |
| Content authoring    | Simple                   | More technical                |
| Frontend integration | Native Next.js ecosystem | Requires additional handling  |

We should not manually write entire tutorials as HTML.

That would make educational content harder to maintain.

## **4.2 Example MDX lesson**

A lesson file could look like this:


## **5.2 Why separate&#x20;**`content/`**&#x20;from&#x20;**`src/`**?**

Because content and application logic have different lifecycles.

A developer might change the authentication system without changing a single tutorial.

An instructor might update 20 lessons without changing the frontend.

Separating these concerns makes the project easier to maintain.

## **5.3 Content organization rules**

- One primary content item per file.
- Use descriptive filenames.
- Keep filenames lowercase.
- Use hyphens instead of spaces.
- Do not use dates as the primary content identifier.
- Avoid deeply nested directories.
- Use metadata for classification rather than relying entirely on directory names.

Example:

```
content/tutorials/linux/file-permissions.mdx
content/tutorials/linux/user-management.mdx
content/tutorials/networking/dns-fundamentals.mdx
content/writeups/web-security/sql-injection-analysis.mdx
```

# **6. Content metadata and TypeScript validation**

Architecture decision

Frontmatter is the metadata at the beginning of an MDX file.

However, we should not trust frontmatter simply because it exists.

A missing slug, invalid difficulty value or malformed publication date could break content pages.

We should validate every content file before deployment.

## **6.1 Required metadata schema**

I recommend the following common metadata structure:

| Field          | Type         | Required          |
| -------------- | ------------ | ----------------- |
| title          | string       | Yes               |
| slug           | string       | Yes               |
| description    | string       | Yes               |
| contentType    | enum         | Yes               |
| category       | string       | Yes               |
| difficulty     | enum         | Yes               |
| author         | string       | Yes               |
| tags           | string array | Yes               |
| published      | boolean      | Yes               |
| publishedAt    | date         | Published content |
| updatedAt      | date         | Yes               |
| readingTime    | number       | Yes               |
| image          | string       | No                |
| prerequisites  | string array | No                |
| relatedContent | string array | No                |

## **6.2 TypeScript content types**

The application should have centralized types.

```

export type ContentType =
  | "tutorial"
  | "article"
  | "writeup"
  | "guide"
  | "reference"
  | "glossary";

export type Difficulty =
  | "beginner"
  | "intermediate"
  | "advanced";

export interface ContentMetadata {
  title: string;
  slug: string;
  description: string;
  contentType: ContentType;
  category: string;
  difficulty: Difficulty;
  author: string;
  tags: string[];
  published: boolean;
  publishedAt?: string;
  updatedAt: string;
  readingTime: number;
  image?: string;
  prerequisites?: string[];
  relatedContent?: string[];
}

export interface EducationalContent {
  metadata: ContentMetadata;
  body: string;
  sourcePath: string;
}

```

## **6.3 Runtime validation**

TypeScript types alone cannot validate external or parsed data at runtime.

We should use Zod for schema validation.

```

import { z } from "zod";

export const ContentSchema = z.object({
  title: z.string().min(3).max(120),
  slug: z.string().regex(/^[a-z0-9-]+$/),
  description: z.string().min(20).max(300),

  contentType: z.enum([
    "tutorial",
    "article",
    "writeup",
    "guide",
    "reference",
    "glossary",
  ]),

  category: z.string().min(1),

  difficulty: z.enum([
    "beginner",
    "intermediate",
    "advanced",
  ]),

  author: z.string().min(1),
  tags: z.array(z.string()),

  published: z.boolean(),
  publishedAt: z.string().optional(),
  updatedAt: z.string(),

  readingTime: z.number().int().positive(),

  image: z.string().optional(),
  prerequisites: z.array(z.string()).optional(),
  relatedContent: z.array(z.string()).optional(),
});

export type ContentMetadata =
  z.infer<typeof ContentSchema>;

```

We should add stricter date validation, publication-date requirements, duplicate-slug detection and reference validation in the actual implementation.

### **Why this matters**

Imagine an instructor writes 50 tutorials and accidentally gives two of them the same slug.

Without validation, one tutorial might overwrite another in the content index.

With validation, the build fails and identifies the conflict.

**Decision:** Invalid content should fail the content validation process before deployment, rather than silently disappearing or breaking production pages.

# **7. Learning path content architecture**

Learning paths require special attention because they connect multiple content files.

We should not duplicate lesson content inside learning path files.

Instead, learning paths should reference existing content by stable identifiers.

## **7.1 Example learning path file**

Location:

`content/paths/linux-fundamentals.yaml`

```

title: "Linux Fundamentals"
slug: "linux-fundamentals"

description: "Learn essential Linux skills."

difficulty: beginner

published: true

estimatedHours: 12

prerequisites: []

objectives:
  - Navigate Linux filesystems
  - Manage files and directories
  - Understand users and permissions
  - Inspect processes and services
  - Understand basic networking

lessons:
  - linux-introduction
  - filesystem-navigation
  - file-management
  - user-management
  - file-permissions
  - process-management
  - services-administration
  - networking-commands
  - ssh-remote-access

```

The actual YAML format will be parsed and validated by TypeScript.

## **7.2 Lesson relationships**

The relationship should be:

- Learning path contains ordered lesson references.
- Each lesson exists as an independent MDX document.
- One lesson can appear in multiple learning paths.
- Progress is calculated separately for each student and path.
- Updating a lesson updates its appearance wherever it is referenced.

This avoids content duplication.

## **7.3 Stable identifiers**

I recommend using a stable content ID in addition to a human-readable slug.

For example:

```
id: "lsn_linux_permissions_001"
slug: "linux-file-permissions"
```

The slug controls the URL.

The ID identifies the content internally.

If we later change the URL, the content ID can remain the same.

This is particularly important when student progress records reference lessons.

**Important:** Never use a lesson's title as its database identity. Titles change.

# **8. Images and asset management**

Images are necessary for technical explanations, diagrams, screenshots and illustrations.

But we have a limited hosting budget.

We need to avoid turning the Vercel deployment into an unnecessarily large media repository.

## **8.1 Image categories**

| Image type               | Example                   |
| ------------------------ | ------------------------- |
| Educational illustration | Linux filesystem diagram  |
| Screenshot               | Terminal output           |
| Architecture diagram     | HTTP request flow         |
| Infographic              | TCP/IP model              |
| Thumbnail                | Tutorial cover            |
| Logo/icon                | Technology identification |

## **8.2 Initial storage recommendation**

Use the Git repository for small, optimized educational assets.

Suggested structure:

```
public/
└── images/
    ├── tutorials/
    │   ├── linux/
    │   └── networking/
    ├── diagrams/
    ├── writeups/
    └── thumbnails/
```

### **Image guidelines**

- Prefer WebP or AVIF where supported.
- Compress screenshots without making technical details unreadable.
- Avoid uploading original multi-megabyte screenshots.
- Use descriptive filenames.
- Provide alternative text.
- Avoid duplicate assets.
- Do not use externally hosted images without checking licensing and reliability.

## **8.3 Future external image storage**

If the content library becomes large, we can move media to an external object-storage provider.

However, we should not introduce another service during initial development.

One limitation: Git is excellent for text, but not an ideal long-term solution for large binary media libraries. We should monitor repository size.

# **10. Reusable educational components**

We should develop a small component library specifically for technical education.

Instead of manually formatting every warning, command explanation and note, instructors can use reusable components.

## **10.1 Proposed content components**

| Component         | Purpose                      |
| ----------------- | ---------------------------- |
| Callout           | Warning, note, tip           |
| Command           | Terminal command             |
| Output            | Expected terminal output     |
| Comparison        | Compare two technologies     |
| LearningObjective | Display lesson objectives    |
| Prerequisites     | Show required knowledge      |
| KeyTakeaways      | Summarize important concepts |
| PracticalTask     | Display assignments          |
| KnowledgeCheck    | Link to a quiz               |
| ResourceList      | Display references           |
| ImageFigure       | Display images with captions |

## **10.2 Example component usage**

```

<Callout type="warning" title="Important">
  Do not run destructive commands
  on production systems.
</Callout>

  ls -lah

  total 16K
  drwxr-xr-x  4 user user 4.0K .
</Output>

  - Permissions control access.
  - Users and groups determine ownership.
</KeyTakeaways>

```

The component library should remain small.

We should only add components when they solve a recurring educational need.

### **10.3 Security consideration**

MDX can execute imported React components and expressions.

Therefore:

- Only trusted instructors or administrators should contribute MDX.
- Never render arbitrary student-submitted MDX.
- Do not allow students to upload executable content.
- Keep content imports restricted to approved components.
- Avoid evaluating arbitrary code during content rendering.

This is an important security boundary for ForgeSec Academy.

# **11. Content quality and lesson standards**

A technically correct tutorial can still be a poor learning resource.

We need a consistent lesson-writing standard.

## **11.1 Recommended lesson structure**

Every substantial tutorial should follow this sequence:

## **ForgeSec lesson template**

1. **Title and introduction**

   Explain what the lesson covers.
2. **Learning objectives**

   Define what students should understand afterward.
3. **Prerequisites**

   Explain what knowledge or tools are needed.
4. **Concept explanation**

   Introduce the technical concept.
5. **Practical demonstration**

   Show commands, examples or configurations.
6. **Expected output**

   Explain what students should observe.
7. **Common mistakes**

   Discuss frequent errors.
8. **Practical assignment**

   Provide a task to perform independently.
9. **Knowledge check**

   Assess understanding.
10. **Summary and references**

    Reinforce important points and provide further reading.

Not every article or write-up needs all ten sections.

Forcing this template onto short reference entries would create unnecessary content.

## **11.2 Technical accuracy requirements**

Every practical lesson should ideally specify:

- Operating system or platform.
- Required privileges.
- Required tools.
- Commands used.
- Expected results.
- Potential risks.
- Verification procedure.
- External references where relevant.

For security-related topics, also identify the authorized environment in which the exercise should be performed.

## **11.3 Content review states**

I recommend a slightly more detailed content lifecycle than simply Draft and Published.

| Status    | Meaning                       |
| --------- | ----------------------------- |
| Draft     | Work in progress              |
| Review    | Awaiting technical review     |
| Approved  | Reviewed and ready to publish |
| Published | Publicly available            |
| Archived  | No longer actively maintained |

Only Approved or Published content should be eligible for publication, depending on the publishing workflow.

This is particularly valuable when the Academy eventually has multiple instructors.

# **12. Content validation and automated quality checks**

P0 — Required infrastructure

We should not depend on instructors manually checking every file.

A small collection of TypeScript scripts can automate much of the validation process.

## **12.1 Required validation checks**

| Check                        | What it prevents            |

| Frontmatter validation       | Missing or invalid metadata |
| Duplicate slug detection     | URL collisions              |
| Duplicate ID detection       | Content identity conflicts  |
| Missing image detection      | Broken images               |
| Broken internal links        | Dead navigation             |
| Missing lesson references    | Invalid learning paths      |
| Invalid categories           | Inconsistent taxonomy       |
| Invalid publication dates    | Incorrect metadata          |
| Unpublished content exposure | Accidental disclosure       |
| Missing required sections    | Incomplete lessons          |

## **12.2 Proposed validation scripts**

```
scripts/
├── validate-content.ts
├── validate-paths.ts
├── validate-assets.ts
├── check-links.ts
└── generate-search-index.ts
```

Each script should perform one clear responsibility.

This follows a useful engineering principle: small scripts are easier to test, debug and maintain than one enormous content-management script.

### **12.4 Build failure policy**

The deployment must fail when:

- A published content item has invalid metadata.
- A learning path references a nonexistent lesson.
- Duplicate content IDs or slugs exist.
- Required assets are missing.
- An invalid content component is used.

We should distinguish between errors and non-blocking warnings.

For example, a missing optional related-content link may generate a warning rather than stopping the deployment.

During the build, a TypeScript script will read published content and generate a compact JSON search index.

## **13.3 Search implementation**

Possible libraries:

- Fuse.js for fuzzy matching.
- MiniSearch for lightweight full-text search.

My recommendation is to start with MiniSearch if we want indexed field-based searching and good scaling for a growing content collection.

We should benchmark the actual index size before choosing.

### **Important optimization**

Do not download the entire search index on every page navigation.

Instead:

- Load it when the student opens search.
- Cache it in the browser.
- Keep the index compact.
- Limit the number of displayed results.
- Use pagination or result limits.

This reduces unnecessary bandwidth.

# **14. Content URLs and SEO architecture**

Educational content should be discoverable through search engines.

We should design URLs carefully because changing them later can affect external links and search rankings.

## **14.1 Proposed URL patterns**

| --------------- | ----------------------------------------- |

| Article         | `/articles/how-dns-works`                 |
| Write-up        | `/writeups/sql-injection-analysis`        |
| Practical guide | `/guides/ssh-configuration`               |
| Glossary        | `/glossary/privilege-escalation`          |
| Category        | `/categories/linux`                       |

We should use a consistent URL pattern for each content type.

## **14.2 SEO metadata**

Each published content item should support:

- SEO title.
- Meta description.
- Canonical URL.
- Open Graph title.
- Open Graph description.
- Social preview image.
- Structured data where appropriate.

These fields can be optional initially, with sensible defaults generated from the normal content metadata.

- XML sitemap.
- Robots.txt.
- Canonical URLs.
- Descriptive page titles.
- Semantic headings.
- Internal linking.
- Image alternative text.
- Correct 404 handling.
- No indexing of private dashboard pages.
- No indexing of unpublished content.

## **14.4 Content URL changes**

If a published slug changes, the system should support a redirect from the old URL.

We should maintain a small redirect configuration in Git.

This avoids broken external links.

# **17. Content architecture and free-tier infrastructure**

This section is particularly important because the Academy must operate without paid hosting initially.

## **17.1 Responsibility separation**

| Service             | Responsibility                              |
| ------------------- | ------------------------------------------- |
| GitHub              | Source code and educational content         |
| Vercel              | Next.js deployment and page delivery        |
| Supabase Auth       | Student authentication                      |
| Supabase PostgreSQL | Student records and application data        |
| Browser             | Client-side search and reading interactions |

We should avoid putting educational content into Supabase just because it is convenient.

The content is largely static. It belongs in Git.

## **17.2 What consumes Supabase resources?**

| Operation               | Supabase required?        |
| ----------------------- | ------------------------- |
| Read public tutorial    | No                        |
| Browse learning paths   | No, if generated from Git |
| Search tutorials        | No                        |
| Read write-up           | No                        |
| View glossary           | No                        |
| Register student        | Yes                       |
| Save bookmark           | Yes                       |
| Track lesson completion | Yes                       |
| Save quiz attempt       | Yes                       |
| Load private dashboard  | Yes                       |

This separation significantly reduces unnecessary database traffic.

## **17.3 What consumes Vercel resources?**

- Building the application.
- Serving static pages and assets.
- Executing dynamic server functions.
- Rendering authenticated pages.
- Serving generated search indexes.

The main optimization is to generate public content pages statically whenever possible.

We should not run a server function for every public lesson request.

## **17.4 Important Vercel consideration**

Static generation does not mean unlimited hosting.

The free plan has usage limits, and commercial usage eligibility and restrictions must be checked before deployment.

We should also avoid configuring a deployment process that rebuilds the entire Academy for every minor administrative action.

For initial development, however, Git-triggered builds are a reasonable approach.

# **18. Content architecture scalability**

We should design for growth without building infrastructure we cannot afford.

## **18.1 Expected growth scenarios**

| Content volume    | Recommended approach                                   |
| ----------------- | ------------------------------------------------------ |
| 10–50 lessons     | MDX + static generation                                |
| 50–200 lessons    | MDX + generated indexes                                |
| 200–500 lessons   | Optimize indexing and build process                    |
| 500–1,000 lessons | Benchmark build time and asset size                    |
| 1,000+ lessons    | Consider content packages or external content delivery |

These are planning thresholds, not hard technical limits.

A well-designed MDX system can support considerably more content. The actual constraints will depend on build duration, memory, repository size, asset volume and deployment quotas.

## **18.2 Scalability principles**

1. Keep public content independent of Supabase.
2. Generate static pages whenever possible.
3. Keep metadata compact.
4. Avoid unnecessary database queries.
5. Avoid loading all content into the browser.
6. Compress images.
7. Separate large assets from source code when necessary.
8. Maintain stable content identifiers.
9. Validate content automatically.
10. Keep the content ingestion system modular.

## **18.3 Future migration options**

If the Academy becomes successful, we can eventually migrate the content system to:

- A headless CMS.
- Git-based remote content storage.
- Dedicated object storage for media.
- A dedicated search service.

None of these migrations should require changing the student progress model if we maintain stable content IDs.

# **19. Recommended technical dependencies**

These are the proposed libraries for the content system.

| Technology                                | Responsibility                                | Priority             |
| ----------------------------------------- | --------------------------------------------- | -------------------- |
| Next.js                                   | Rendering and routing                         | Required             |
| TypeScript                                | Application and scripts                       | Required             |
| MDX                                       | Educational content                           | Required             |
| `@next/mdx` or compatible MDX integration | MDX rendering                                 | Required             |
| Zod                                       | Metadata validation                           | Required             |
| Gray-matter                               | Frontmatter parsing, if using a custom loader | Required if selected |
| MiniSearch                                | Client-side search                            | Recommended          |
| Shiki                                     | Code syntax highlighting                      | Recommended          |
| Mermaid                                   | Technical diagrams                            | Recommended          |
| ESLint                                    | Code quality                                  | Required             |

A technical distinction: `@next/mdx` and a custom filesystem content loader are not interchangeable configuration choices. We should select one content-loading approach during the implementation architecture phase and avoid unnecessary duplicate parsing systems.

I recommend a filesystem-based content layer with a centralized TypeScript loader, metadata validation and controlled MDX compilation.

We should also pin dependency versions and verify compatibility with the selected Next.js version.

## **21.1 Non-negotiable content rules**

- Never store public tutorial bodies in Supabase.
- Never make students register to read public lessons.
- Every content item must have a stable identifier.
- Validate metadata before deployment.
- Prevent duplicate slugs and IDs.
- Use reusable educational components.
- Keep MDX restricted to trusted contributors.
- Keep content independent of the UI implementation.
- Support technical diagrams and code blocks.
- Preserve revision history.
- Avoid unnecessary paid content services.
