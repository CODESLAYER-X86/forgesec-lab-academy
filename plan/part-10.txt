# **Part 10 — Practical Assignments & Hands-on Learning System**

## **Building practical cybersecurity skills without hosting labs, VMs or practice servers**

**Objective:** Design a practical learning system where students apply what they learn using their own computers, locally installed tools and explicitly authorized real-world systems.

This is particularly important for FORGESEC ACADEMY because practical cybersecurity education can become expensive if every student requires a hosted virtual machine or dedicated lab environment.

My recommendation is to build an **assignment-driven learning system**, not a hosted cyber range.

Students receive:

- Practical tasks.
- Step-by-step instructions.
- Expected outcomes.
- Verification procedures.
- Safety boundaries.
- Completion tracking.

The Academy provides the learning structure, while students provide their own computing environments.

## **1. Core architecture**

The practical assignment system will be another internal Next.js module.

**FORGESEC ACADEMY**

Assignments · Instructions · Verification · Progress

**Student's Own Environment**

Linux computer · Terminal · Browser · Networking tools

**Student Verification**

Commands · Expected output · Screenshots · Explanations

**Supabase PostgreSQL**

Assignment progress and optional submissions

The Academy server does not execute student commands.

That distinction is important: a student running `chmod` on their own computer is completely different from allowing arbitrary users to execute commands on your hosting infrastructure.

### **What the Academy will NOT provide initially**

- Hosted Linux terminals.
- Browser-based Kali Linux.
- Virtual machines.
- Docker lab environments.
- Remote shell access.
- Student-controlled server processes.
- Automated execution of submitted scripts.
- Vulnerable web application hosting.

These can be considered later if the Academy has funding and a clear operational need.

## **2. Assignment categories**

Organize assignments according to the learning topics.

| Category             | Example practical activities                              |
| -------------------- | --------------------------------------------------------- |
| Linux Fundamentals   | File navigation, permissions, users and processes         |
| Linux Administration | Services, system logs and package management              |
| Networking           | IP addressing, DNS, routing and connectivity              |
| SSH                  | Key generation and remote authentication                  |
| Web Technologies     | HTTP requests, headers and browser developer tools        |
| Web Security         | Understanding security headers and common vulnerabilities |
| Reconnaissance       | Passive information gathering on approved targets         |
| Defensive Security   | Log analysis, basic hardening and monitoring              |

Start with Linux, networking and SSH because these establish the foundations needed for more advanced cybersecurity work.

### **Recommended assignment difficulty**



Beginner

&#x20;Basic commands and simple observations.





Intermediate

&#x20;Multiple commands, troubleshooting and interpretation.





Advanced

&#x20;Combining multiple skills, analyzing evidence and documenting findings.



Do not use difficulty labels merely to make assignments look impressive. Base them on prerequisites and the amount of independent problem-solving required.

## **3. Assignment structure**

Every practical assignment should follow the same template.

Beginner

Linux Fundamentals

# **Explore the Linux Filesystem**

**Objective**

Learn how Linux organizes directories and how to navigate the filesystem.

**Requirements**

- Access to a Linux terminal.
- A Linux computer or an existing authorized Linux environment.

**Tasks**

1. Display your current working directory.
2. List files in the current directory.
3. Display hidden files.
4. Navigate to your home directory.
5. Identify the root directory.

**Commands to investigate**

```
pwd
ls
ls -la
cd ~
ls /
```

**Expected outcome**

You should be able to identify your current directory, inspect directory contents and navigate between directories.

**Verification**

- Run the commands.
- Explain what each command does.
- Record the output of at least three commands.

**Completion requirement**

Submit your explanation and mark the assignment as completed after verifying the tasks yourself.

Example assignment presentation.

## **4. Assignment workflow**

The assignment process should be predictable.

1. **Discover**

   Student finds an assignment from a lesson or assignment catalogue.
2. **Read**

   Student reviews the objective, prerequisites and safety notes.
3. **Perform**

   Student executes the tasks in their own environment.
4. **Verify**

   Student compares their results with the expected outcome.
5. **Document**

   Student records relevant evidence or explanations.
6. **Complete**

   Student marks the assignment completed.

### **Assignment statuses**

Use three statuses in the application:

| Status      | Meaning                             |
| ----------- | ----------------------------------- |
| Not started | No recorded activity                |
| Started     | Student has begun                   |
| Completed   | Student reports completing the task |

The `assignment_progress` table from Part 06 currently has `started` and `completed`. An absent row represents Not started.

This is sufficient for the initial release.

## **5. Verification system**

This is where we need to be particularly careful.

Since the Academy does not execute commands or control student computers, it cannot automatically prove that a task was completed.

There are three practical verification levels.

### **Level 1 — Self-verification**

P0 · Launch

Students compare their output with the expected outcome.

Example:

```
whoami
id
groups
```

They should be able to explain:

- The current username.
- Their user ID.
- Their group memberships.

The student marks the task complete.

This is inexpensive and easy to implement.

### **Level 2 — Evidence submission**

P1 · Later

Students submit evidence such as:

- Terminal screenshots.
- Command output.
- Short explanations.
- Configuration excerpts.
- A small text report.

The Academy stores the submission and an instructor can review it.

This requires additional tables and potentially file storage.

### **Level 3 — Instructor verification**

P2 · Later

An instructor reviews the submission and assigns a result:

- Accepted.
- Needs correction.
- Rejected.
- Requires additional explanation.

This provides more meaningful verification, particularly for advanced practical assignments.

**My recommendation:** Launch with Level 1. Do not introduce evidence uploads until there is an actual reason to review student submissions.

## **6. Assignment and lesson integration**

Assignments should appear naturally inside the educational content.

For example:

**Lesson: Linux File Permissions**

The lesson explains:

- File ownership.
- Read, write and execute permissions.
- `chmod`.
- `chown`.
- Symbolic and numeric permissions.

Practical assignment

**Change and inspect file permissions**

Create a test file, change its permissions and verify the result using `ls -l`.

Estimated time: 10 minutes

**Open assignment →**

### **Integration rules**

- A lesson can reference multiple assignments.
- An assignment can reference one primary lesson.
- Assignments can have prerequisites.
- Completing an assignment does not automatically complete a lesson.
- Completing a lesson does not automatically complete an assignment.

Keep lesson progress and assignment progress separate.

This makes the progress system more honest.

## **7. Safety and authorization rules**

Cybersecurity assignments require explicit boundaries.

A task should never leave students guessing whether they are allowed to test a system.

### **Safe assignment categories**

| Activity                                          | Initial policy                  |
| ------------------------------------------------- | ------------------------------- |
| Linux commands on own computer                    | Allowed                         |
| Local configuration inspection                    | Allowed                         |
| Local networking diagnostics                      | Allowed                         |
| Testing own applications                          | Allowed                         |
| Testing systems with explicit authorization       | Allowed within scope            |
| Passive research using public information         | Allowed within applicable rules |
| Scanning random public IP addresses               | Not an assignment target        |
| Exploiting third-party systems without permission | Prohibited                      |
| Disruptive testing against public services        | Prohibited                      |

### **Every security assignment should include**

1. Authorized target definition.
2. Permitted actions.
3. Prohibited actions.
4. Expected impact.
5. Cleanup instructions.
6. Stop conditions.

For example, a networking exercise can ask students to inspect their own network configuration rather than scan an arbitrary public address.

The objective is to teach real security skills without encouraging unauthorized activity.

### **RLS requirements**

- Students can read published assignments.

- Admins can manage assignment publication.

## **Part 10 — Final architectural decisions**

| Area                     | Decision                               |
| ------------------------ | -------------------------------------- |
| Practical learning model | Assignment-driven                      |
| Student environment      | Own computer or authorized environment |
| Hosted infrastructure    | None initially                         |
| Command execution        | Never on Academy server                |
| Assignment content       | PostgreSQL initially                   |
| Progress storage         | PostgreSQL                             |
| Completion verification  | Self-reported                          |
| Evidence submission      | Future feature                         |
| Instructor review        | Future feature                         |
| Lesson integration       | Related lesson IDs                     |
| Security boundaries      | Explicit authorization and scope       |
| Admin management         | Internal Next.js interface             |

**My recommendation:** Invest in the quality of practical assignments rather than infrastructure. A well-designed Linux exercise that teaches students how to investigate, execute and explain commands can be more valuable than a poorly designed hosted lab.

The Academy's advantage should be its teaching quality and practical learning methodology, not the number of servers it operates.
