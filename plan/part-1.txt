## **1. Executive summary**

ForgeSec Academy will be a free, web-based cybersecurity education platform developed and maintained under FORGESEC LABS.

Its primary purpose is to make cybersecurity education accessible through structured tutorials, practical assignments, technical explanations, research, and learning resources.

The platform will prioritize:

1. High-quality educational content.
2. Practical learning using students' own environments.
3. Structured learning paths.
4. Student progress tracking.
5. A professional publishing and administration system.
6. Lightweight architecture compatible with free hosting.

**The central philosophy: Teach the concept, demonstrate the technique, assign the practical task, and explain how to verify the result.**

We are building an educational platform, not a cyber-range provider.

Cybersecurity education and technical knowledge platform.

ForgeSec Academy will differentiate itself through practical, structured, technically accurate educational content rather than simply collecting articles from different sources.

# **3. Product objectives**

We should distinguish between educational objectives and business objectives.

### **3.1 Educational objectives**

- Make complex cybersecurity concepts understandable.
- Provide a logical learning sequence.
- Connect theory with practical work.
- Encourage independent experimentation.
- Develop problem-solving skills.
- Teach responsible and authorized security practices.
- Help students become independent learners.

### **3.2 Organizational objectives**

- Establish ForgeSec as a credible cybersecurity education brand.
- Demonstrate the technical expertise of its instructors and contributors.
- Build an audience around cybersecurity education.
- Publish technical research and practical write-ups.
- Create a foundation for future educational initiatives.

### **3.3 Personal credibility objective**

An important consideration is that the platform should demonstrate teaching ability through actual educational output.

A student should be able to read a lesson and conclude:

- The instructor understands the subject.
- The explanation is technically correct.
- The practical instructions are reproducible.
- The material has been organized thoughtfully.

This is more valuable than publishing a large number of shallow tutorials.

# **6. Educational content standards**

This is one of the most important sections of the entire project.

ForgeSec should have a consistent teaching methodology.

## **6.1 Standard lesson structure**

Every technical lesson should follow a recognizable structure:

## **Example lesson structure**

**Topic: Linux File Permissions**

1. **Introduction**

   What are file permissions?
2. **Why it matters**

   Why does Linux control file access?
3. **Concept explanation**

   Owner, group, others, read, write and execute.
4. **Practical demonstration**

   Commands such as `ls -l`, `chmod` and `chown`.
5. **Expected output**

   Explain what students should observe.
6. **Practical assignment**

   Give the student a task to perform on their own Linux machine.
7. **Verification**

   Show how to confirm that the task was completed correctly.
8. **Knowledge check**

   A few questions testing understanding.

Not every article needs all eight sections. For example, a research write-up and a glossary entry should have different structures.

## **6.2 Writing standards**

The following standards should apply:

- Use straightforward technical English.
- Avoid unnecessary theoretical explanations.
- Explain unfamiliar terminology.
- Use realistic command examples.
- Include expected outputs where useful.
- Explain dangerous commands before asking students to run them.
- Never encourage testing against systems without authorization.
- Provide references for important technical claims.
- Verify practical instructions before publishing.

## **6.3 Practical learning philosophy**

The platform must not confuse reading a command with knowing how to use it.

For example:

| Weak teaching           | Better teaching                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------ |
| `systemctl restart ssh` | Explain what systemd does, why SSH might need restarting, and how to verify service status |
| Explain `chmod`         | Assign a file-permission task and ask students to verify access                            |
| Explain SSH             | Ask students to connect to an authorized remote server                                     |
| Explain Nmap            | Demonstrate scanning a local or authorized target                                          |

The analogy is learning to drive: reading about the accelerator does not teach you how to drive. The learner needs to operate the actual vehicle in a safe, authorized setting.

# **7. Student learning model**

We should design the student journey around progressive learning.

## **Student journey**

1. **Discover**

   Student finds a topic through search, the homepage or a learning roadmap.
2. **Understand**

   Student reads the lesson and studies examples.
3. **Practice**

   Student performs the assignment on their own machine or an authorized environment.
4. **Verify**

   Student checks the expected result and completes a knowledge check.
5. **Track**

   Student records lesson completion and monitors learning progress.
6. **Advance**

   Student follows the next recommended lesson or learning path.

### **Guest versus registered student**

I recommend two access levels for learners.

| Capability                 | Guest | Registered student |
| -------------------------- | ----- | ------------------ |
| Read tutorials             | Yes   | Yes                |
| Read write-ups             | Yes   | Yes                |
| View roadmaps              | Yes   | Yes                |
| Search content             | Yes   | Yes                |
| Take public quizzes        | Yes   | Yes                |
| Save bookmarks             | No    | Yes                |
| Track progress             | No    | Yes                |
| Personal dashboard         | No    | Yes                |
| Maintain learning history  | No    | Yes                |
| Participate in discussions | No    | Yes, if enabled    |

This ensures that registration improves the experience without obstructing access to education.

# **8. Technical and infrastructure constraints**

These constraints are product requirements, not matters to postpone until deployment.

## **8.1 Infrastructure principles**

1. No mandatory paid services.
2. No permanently running backend server.
3. No arbitrary code execution.
4. No hosted laboratory infrastructure.
5. No unnecessary third-party API dependencies.
6. Static content should be served efficiently.
7. Database usage should be minimized.
8. All critical functionality should work within the free-tier resource limits.

## **8.2 Proposed infrastructure allocation**

| Requirement                | Primary solution                      |
| -------------------------- | ------------------------------------- |
| Website hosting            | Vercel                                |
| Public educational content | Git repository / MDX                  |
| Application database       | Supabase PostgreSQL                   |
| Student authentication     | Supabase Auth                         |
| Student progress           | Supabase                              |
| User bookmarks             | Supabase                              |
| Static images              | Optimized repository assets initially |
| Source control             | GitHub                                |
| Application language       | TypeScript                            |
| Server-side execution      | Next.js Node.js runtime               |

## **8.3 Performance requirements**

- Public educational pages should be statically generated wherever practical.
- Avoid loading unnecessary JavaScript.
- Use responsive images.
- Implement pagination for large content collections.
- Avoid fetching all lessons or records at once.
- Provide useful loading, empty and error states.
- Ensure the platform works on mobile devices.

## **8.4 Security requirements**

Security must be treated as a core requirement because this is a cybersecurity education platform.

- Enforce role-based access control.
- Enable Supabase Row Level Security.
- Validate user inputs on the server.
- Protect administrative routes.
- Never expose service-role credentials in client-side code.
- Apply authorization checks to every sensitive operation.
- Prevent unauthorized modification of learning records.
- Sanitize and validate user-generated content.
- Protect against common web vulnerabilities.

# **9. Product principles and non-negotiable rules**

These principles will guide future architectural and implementation decisions.

| Principle        | Meaning                                                   |
| ---------------- | --------------------------------------------------------- |
| Content-first    | Education comes before platform complexity                |
| Practical-first  | Explain how knowledge applies in reality                  |
| Free-first       | No paid infrastructure dependency                         |
| TypeScript-first | Application code uses TypeScript                          |
| Static-first     | Minimize unnecessary server execution                     |
| Security-first   | Secure defaults and strict authorization                  |
| Mobile-friendly  | Responsive educational experience                         |
| Expandable       | New domains can be added without restructuring everything |
| Maintainable     | Prefer simple, understandable architecture                |

**A critical distinction:** Free-first does not mean insecure or unreliable. We should not sacrifice security to save a small amount of infrastructure cost.

# **10. Roles and permissions**

The initial platform should support a small, clearly defined role system.

| Role       | Responsibilities                                        |
| ---------- | ------------------------------------------------------- |
| Guest      | Read public content                                     |
| Student    | Track progress, save content and take quizzes           |
| Instructor | Create and manage assigned educational content          |
| Admin      | Manage users, content, settings and platform operations |

### **Permission philosophy**

- Students cannot modify other students' records.
- Instructors should only manage content they are authorized to manage.
- Admin privileges should be restricted.
- Public educational content should remain readable without authentication.

We should implement permissions centrally rather than scattering role checks throughout frontend components.

# **12. Risks and limitations**

We should acknowledge the limitations before implementation.

| Risk                                    | Mitigation                                          |
| --------------------------------------- | --------------------------------------------------- |
| Supabase free project pauses            | Plan around inactivity and operational availability |
| Database storage fills                  | Store educational content in Git                    |
| Vercel quotas exceeded                  | Static generation, caching and efficient functions  |
| Content becomes outdated                | Maintain references and review dates                |
| Inaccurate technical instructions       | Test commands before publishing                     |
| Student progress manipulation           | Server-side authorization and database constraints  |
| Spam in discussions                     | Moderation and rate limiting                        |
| Content production becomes overwhelming | Start with one learning domain                      |
| Dependence on one hosting provider      | Keep deployment architecture portable               |

One additional concern: certificates should not become a priority. Without a meaningful assessment process, certificates can damage credibility rather than improve it.
